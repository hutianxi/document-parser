document-parser

把 Word / PDF / PPT 统一解析成 text、tables、images 三个集合的 Java 8 库。 三种格式返回同一套结构，换格式只换类名；表格统一还原成「表头 + 行对象」，headers 可以直接当列清单用。

它解决什么问题

业务上常要「把客户上传的合同、报告、汇报 PPT 里的文字和表格抽出来入库」。这三种格式的底层模型完全不同： Word 有真正的表格对象和合并标记，PDF 只有画出来的线段和散落的文字，PPT 是一页页形状。 各写一套解析、各返回一种结构，上层就要写三份入库逻辑，改一处规则要改三个地方。

格式差异关在解析器里

WordParser / PdfParser / PptParser 都返回 Map<String,Object>， 键固定是 text / tables / images。加一种新格式只需再写一个解析器。

headers 就是列清单

每组表的 headers 逐个等于每一行的键，合并单元格一律拆开回填，所以每行键数量恒定， 建表、映射 DTO、写 INSERT 都不用特殊处理。

确定、无状态、不出进程

同一份文件重复解析结果完全相同，可以写成断言进 CI；纯静态方法、可并发；不联网， 外链图片只记元信息不下载。

快速开始

Aspose 的三个构件不在 Maven Central 上，引用方需要在自己的 pom 里声明 Aspose 仓库。

<repositories>
    <repository>
        <id>aspose</id>
        <url>https://repository.aspose.com/repo/</url>
    </repository>
</repositories>

<dependency>
    <groupId>cn.net.tianxi</groupId>
    <artifactId>document-parser</artifactId>
    <version>1.1.1</version>
</dependency>
Map<String, Object> result = WordParser.parse("D:/a.docx", "销售");   // PdfParser / PptParser 同名同参
String json = WordParser.toJson(result);

不想写代码就想看某个文档被解析成什么样，跑仓库自带的 PrintResultTest（不断言、只打印）：

mvn -B test -Dtest=PrintResultTest
mvn -B test -Dtest=PrintResultTest#printAnyDocument -Ddoc="D:/你的文档.docx"

键内容
text全文段落，用 \n 拼接；表格里的文字不在这里重复。域代码丢掉、域缓存结果保留，软换行/分页符换成空格。
tables一张物理表有几组表头就有几个元素，每个元素的 rows 只装属于它的数据行；headers 与每行键逐个相等。
images元信息（文件名、类型、宽高、字节数、SHA-1 指纹 contentId）任何模式都给；内容去向由 ImageMode 决定：META（默认）/ BASE64 / BYTES / FILE。

与 OCR 的区别

两条完全不同的技术路线：本项目解析格式对象模型，读的是文件里本来就存着的字符数据；OCR 把页面渲染成图，从像素推断字形。

维度document-parser（读文字层）OCR（图像识别）
输入前提电子原生文档：Word 存的 docx、程序导出的 pdf、PowerPoint 存的 pptx任何能变成图片的页面，包括扫描件、拍照件
文字从哪来文件内的字符数据，原样读出从像素推断，存在误识率
数字与金额与原文逐字符一致（合计 行读到的是域缓存值 2096.30/1796.10，183 个测试逐格断言）0/O、1/l、8/B、小数点这类字形易混，金额通常要人工复核
表格结构拿到真结构：合并单元格标记、两行表头、单元格内嵌套子表都能识别并拆开回填靠框线检测还原；无边框表、跨页断表、合并格容易错行错列
结果稳定性同一份文件重复解析结果完全相同，可以写成断言进 CI换引擎版本、换分辨率、换二值化参数结果会变，难做回归
部署形态一个 jar + 三个 Aspose 依赖，进程内完成，不联网一般要额外装识别引擎/模型，或把文档上传到第三方云服务
扫描件 / 图片型 PDF读不出来（没有文字层），这是文档里写明的边界唯一可行的路线
诚实边界：本页不给 OCR 的准确率或耗时数字。仓库里没有跑过任何 OCR 引擎，编不出可复现的实测值； 要横向对比，请拿同一批文件在两边各跑一遍再比。上表右列写的是 OCR 这条路线的固有特征，不是某个产品的实测结果。

本项目自己的单文件耗时是实测的（三份样例，评估模式、无 .lic；同一份代码在 JDK 8 下连跑两轮 mvn test，取两轮区间）：

应用场景

适合直接上的场景，以及明确不适合、需要换方案的场景。

场景怎么用
合同 / 报告 / 台账入库客户上传的 docx 一次解析成正文 + 结构化表 + 附件图，headers 直接映射数据库列
RAG 与知识库切片text 做语义切片，tables 保留结构单独存，images 用 ImageMode.FILE 落盘再传对象存储
BI / 报表汇聚下属单位交上来的同模板 Word / PDF 报表，注册表头后列名固定，直接批量入仓
财务与审计留痕金额取的是文件里的原值（域缓存结果），不是识别值，可追溯
多格式一致性核对同一份报告的 docx / pdf / pptx 三版逐格对比（CrossFormatTest 就是这么干的）
PPT 汇报内容归档正片文字、表格、图片一次抽出，备注页读不到
扫描件 + 电子件混合的收件流程先探一遍：text 与 tables 都空说明没有文字层，降级走 OCR。这条分流判据是建议，仓库里没有扫描件样例，未做实测

明确不适合

  • 扫描件、拍照件、图片型 PDF（没有文字层，必须 OCR）
  • 图表（Chart）里的数据、SmartArt 文字、嵌入的 Excel/Word（OLE 对象）内容
  • Word 的页眉页脚、脚注尾注、批注；PPT 的备注页、母版、版式页文字
  • 需要保留版面的场景（分页位置、字体、坐标、原样转 HTML/PDF）

已知限制

  • PDF 里没有边框线的表格会被当成普通段落进 text
  • PDF 跨页断行特别高（下边界离页底超过页高 1/5）且未注册表头依据时，一张表会拆成两组
  • Word 导出 PDF 会重算域，缓存的 SUM(ABOVE) 结果会丢（要金额请用 docx）
  • BASE64/BYTES 模式把图片字节留在结果里，图片多的文档请用 FILE 或 META
