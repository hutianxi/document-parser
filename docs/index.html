document-parser

把 Word / PDF / PPT 统一解析成 text、tables、images 三个集合的 Java 8 库。 三种格式返回同一套结构，换格式只换类名；表格统一还原成「表头 + 行对象」，headers 可以直接当列清单用。

它解决什么问题

业务上常要「把客户上传的合同、报告、汇报 PPT 里的文字和表格抽出来入库」。这三种格式的底层模型完全不同： Word 有真正的表格对象和合并标记，PDF 只有画出来的线段和散落的文字，PPT 是一页页形状。 各写一套解析、各返回一种结构，上层就要写三份入库逻辑，改一处规则要改三个地方。

格式差异关在解析器里

WordParser / PdfParser / PptParser 都返回 Map<String,Object>， 键固定是 text / tables / images。加一种新格式只需再写一个解析器。

headers 就是列清单

每组表的 headers 逐个等于每一行的键，合并单元格一律拆开回填，所以每行键数量恒定， 建表、映射 DTO、写 INSERT 都不用特殊处理。注册表头时起的名字会变成这组的 name 键， 取数用 tablesByName / rowsByName，不必记住第几组。

确定、无状态、不出进程

同一份文件重复解析结果完全相同，可以写成断言进 CI；纯静态方法、可并发；不联网， 外链图片只记元信息不下载。

快速开始

Aspose 的三个构件不在 Maven Central 上，引用方需要在自己的 pom 里声明 Aspose 仓库。

<repositories>
    <repository>
        <id>aspose</id>
        <url>https://repository.aspose.com/repo/</url>
    </repository>
</repositories>

<dependency>
    <groupId>cn.net.tianxi</groupId>
    <artifactId>document-parser</artifactId>
    <version>1.2.0</version>
</dependency>
Map<String, Object> result = WordParser.parse("D:/a.docx", "销售");   // PdfParser / PptParser 同名同参
String json = WordParser.toJson(result);

要入库的那几张表可以在注册表头时起个名字，之后按名字取组取行，不必去数 tables 下标（只有命中了注册表头的组才带 name 键）。注意：name / tablesByName / rowsByName 与 source 键是 1.2.0 新增的，1.1.1 产物里没有它们。

WordParser.Options opts = WordParser.options()
        .headers("片区", "区域", "销售额", "回款率", "销售额", "回款率", "备注").name("季度明细")
        .headers("片区", "年度目标", "完成率").name("年度目标")   // 末列在文档里没有标题，只注册前三个就命中
        .fullRow(WordParser.FullRow.DROP);
Map<String, Object> result = WordParser.parse("D:/a.docx", opts);

List<Map<String, Object>> groups = WordParser.tablesByName(result, "季度明细");
for (Map<String, String> row : WordParser.rowsByName(result, "年度目标")) {
    // 一个名字可以命中多组（样例里同一张物理表被 2025/2026 两段表头切成两组），
    // rowsByName 按 tables 里的顺序把它们摊平成一个列表，直接逐行入库
}

不想写代码就想看某个文档被解析成什么样，跑仓库自带的 PrintResultTest（不断言、只打印）：

mvn -B test -Dtest=PrintResultTest

返回结构

下面是 src/test/resources/word/sales-report.docx 的实测输出（默认 ImageMode.META，图片只有元信息）。

{
  "text": "2025 年度华东区销售业绩报告\n报告页次：3 页\n归档编号：\n…",
  "tables": [
    { "headers": ["片区", "区域", "销售额", "回款率", "销售额-5", "回款率-6", "备注"],
      "rows": [ { "片区": "华东大区", "区域": "上海", "销售额": "1280", "回款率": "92%",
                  "销售额-5": "1465", "回款率-6": "95%", "备注": "超额完成" } ],
      "source": { "page": 1 } }
  ],
  "images": [
    { "fileName": "image-1.png", "type": "PNG", "width": 1024, "height": 768,
      "size": 670939, "contentId": "487e915db2c53907e8c1551aeaffea235423210c" }
  ]
}
键内容
text全文段落，用 \n 拼接；表格里的文字不在这里重复。域代码丢掉、域缓存结果保留，软换行/分页符换成空格。
tables一张物理表有几组表头就有几个元素，每个元素的 rows 只装属于它的数据行；headers 与每行键逐个相等。每组另带一个 source：page 是这组的起始位置（docx／pdf 的页码、pptx 的幻灯片序号，都从 1 起），跨页的长表再加 lastPage；三种格式含义相同，由 Tables.markSource 统一写。不要这个键就 Options.source(false)——三种格式一起生效，关掉后每组只剩 headers 与 rows，docx 因此不必算整篇版面。注册表头时起了名字的组还多一个 name 键（键顺序固定 headers → rows → name → source），配合 WordParser.tablesByName / rowsByName 按名字取数；只有「注册了、且这组表头命中了那条注册」才写，静默输出里一个 name 都没有。
images元信息（文件名、类型、宽高、字节数、SHA-1 指纹 contentId）任何模式都给；内容去向由 ImageMode 决定：META（默认）/ BASE64 / BYTES / FILE。

与 OCR 的区别

两条完全不同的技术路线：本项目解析格式对象模型，读的是文件里本来就存着的字符数据；OCR 把页面渲染成图，从像素推断字形。

维度document-parser（读文字层）OCR（图像识别）
输入前提电子原生文档：Word 存的 docx、程序导出的 pdf、PowerPoint 存的 pptx任何能变成图片的页面，包括扫描件、拍照件
文字从哪来文件内的字符数据，原样读出从像素推断，存在误识率
数字与金额与原文逐字符一致（合计 行读到的是域缓存值 2096.30/1796.10，242 个测试逐格断言）0/O、1/l、8/B、小数点这类字形易混，金额通常要人工复核
表格结构拿到真结构：合并单元格标记、两行表头、单元格内嵌套子表都能识别并拆开回填靠框线检测还原；无边框表、跨页断表、合并格容易错行错列
结果稳定性同一份文件重复解析结果完全相同，可以写成断言进 CI换引擎版本、换分辨率、换二值化参数结果会变，难做回归
部署形态一个 jar + 三个 Aspose 依赖，进程内完成，不联网一般要额外装识别引擎/模型，或把文档上传到第三方云服务
扫描件 / 图片型 PDF读不出来（没有文字层），这是文档里写明的边界唯一可行的路线
诚实边界：本页不给 OCR 的准确率或耗时数字。仓库里没有跑过任何 OCR 引擎，编不出可复现的实测值； 要横向对比，请拿同一批文件在两边各跑一遍再比。上表右列写的是 OCR 这条路线的固有特征，不是某个产品的实测结果。

本项目自己的单文件耗时是实测的（三份样例，评估模式、无 .lic；用一次性探针测试类在 JDK 8 下连跑两轮 mvn test，取两轮区间 —— 探针跑完就删，仓库里没有它，要复现得自己写一个）：

  • docx 的 source 键要付版面构建：LayoutCollector 的构造本身 0ms，第一次 getStartPageIndex 才把整篇版面算出来（探针拆开实测：加载 16–24ms、建 collector 0ms、5 张表 17 次取页码 98–131ms），这就是「之后」那一列从上一版的 23–30ms 涨到 83–227ms 的原因。不要页码就 Options.source(false)，Word 侧连 collector 都不建，同一份样例实测回到 11–35ms（一次性探针在同一 JVM 里把开／关交替各跑 6 次、连跑两轮，避免后跑的那一种白捡 JIT 预热：开 74–254ms 对 关 11–35ms，两轮里「关」的最大值都低于同一轮「开」的最小值；探针跑完就删）。PDF／PPT 的页码解析时本来就有，开关对它们没有可测差异（同轮 pdf 681–960ms 对 696–984ms、pptx 46–86ms 对 44–71ms），但这个键三种格式一起消失。
  • PDF 那 700–1200 ms 花在 TableAbsorber 的几何聚类、跨页并表和每页第二遍流式引擎上，与页数、线段数量相关，不是文件体积决定的。第二遍是上一版的 1.3 倍左右：同一 JVM 里拆开实测 3 页 —— 只跑线段 478ms、只跑流式 615ms、两遍 922ms。

应用场景

适合直接上的场景，以及明确不适合、需要换方案的场景。

场景怎么用
合同 / 报告 / 台账入库客户上传的 docx 一次解析成正文 + 结构化表 + 附件图，headers 直接映射数据库列；要入库的那几张表注册时起个名字，之后用 rowsByName 按名字取行，不必去数 tables 下标
RAG 与知识库切片text 做语义切片，tables 保留结构单独存，images 用 ImageMode.FILE 落盘再传对象存储
BI / 报表汇聚下属单位交上来的同模板 Word / PDF 报表，注册表头后列名固定，直接批量入仓
财务与审计留痕金额取的是文件里的原值（域缓存结果），不是识别值，可追溯
多格式一致性核对同一份报告的 docx / pdf / pptx 三版逐格对比（CrossFormatTest 就是这么干的）
PPT 汇报内容归档正片文字、表格、图片一次抽出，备注页读不到
扫描件 + 电子件混合的收件流程先探一遍：text 与 tables 都空说明没有文字层，降级走 OCR。这条分流判据是建议，仓库里没有扫描件样例，未做实测

明确不适合

  • 扫描件、拍照件、图片型 PDF（没有文字层，必须 OCR）
  • 图表（Chart）里的数据、SmartArt 文字、嵌入的 Excel/Word（OLE 对象）内容
  • Word 的页眉页脚、脚注尾注、批注；PPT 的备注页、母版、版式页文字
  • 需要保留版面的场景（分页位置、字体、坐标、原样转 HTML/PDF）

已知限制

  • PDF 里没有边框线的表格：只有每行格数相同的才补读得出来（实测无边框样例 0 组 → 3 组），行数不齐的（首行是大标题那种）仍在 text 里；补读的代价是用制表位排齐的几行散文本可能被当成一张表（已实测，测试里钉住了这条误报）
  • PDF 跨页断行特别高（下边界离页底超过页高 1/5）且未注册表头依据时，一张表会拆成两组
  • Word 导出 PDF 会重算域，缓存的 SUM(ABOVE) 结果会丢（要金额请用 docx）
  • BASE64/BYTES 模式把图片字节留在结果里，图片多的文档请用 FILE 或 META
  • 多级表头：分组算法逐行比对网格，连续表头行合并完还会拿合并结果再比一次，所以注册「两行合并后那一行」时 docx／pdf／pptx 都命中（容忍度 0 也命中）；照上层那一行注册才有格式差异 —— docx 13 行、pptx 8 行（下层漏进数据）、pdf 命不中。跨格式共用一份注册时，把上下两种写法各注册一次、起同一个名字最稳，实测三份样例行数一字未变；name 只在命中注册组的那几组上写

贡献

  • Fork → 从 main 切分支 → mvn -B clean test 全绿 → 提 PR
  • 行为变更要附修改前后的端到端 JSON 对比
  • 改了对外可见的行为（返回结构的键、公开方法、行为口径），要在 CHANGELOG.md / CHANGELOG.en.md 最上方的未发布一节补一条，并带上样例上的实测数字
  • 两个仓库都配了保护分支：只有维护者能直接推送与合并，贡献走 PR
